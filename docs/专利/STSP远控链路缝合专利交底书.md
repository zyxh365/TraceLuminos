## 四、技术领域

本发明涉及分布式系统可观测性和车联网远程控制技术领域，尤其涉及一种在终端设备不具备标准链路追踪能力的情况下，利用业务关联标识对远控指令下发链路与执行结果上报链路进行恢复、关联和缝合的方法、系统、设备及存储介质。

## 五、背景技术

### 5.1 车联网远控链路的观测问题

在车联网远控场景中，一条完整业务链路通常为：

`App -> TSP网关 -> 远控服务 -> 下行网关/消息中间件 -> TBox -> 上行网关/消息中间件 -> 远控服务 -> 推送服务 -> App`

其中可能涉及 HTTP、Kafka、MQTT、Netty 长连接、EMQX、短信唤醒和消息推送等多种协议与组件。

现有分布式链路追踪方案一般依赖标准 `TraceContext` 在服务之间透传，各节点基于统一 Trace 上报 Span，最终在观测平台中拼装为完整调用链。然而，TBox 属于终端黑盒设备，通常不具备标准观测能力，导致链路在设备边界发生断裂。

### 5.2 现有技术的局限

现有方案至少存在如下不足：

1. TBox 无法部署 OpenTelemetry 等埋点组件，无法透传标准 Trace 上下文。
2. 指令由云端发往 TBox 后，链路通常终止于云侧最后一个下发节点。
3. TBox 上报结果时，云端只能重新创建新的 Trace，无法自动恢复到原始下发链路中。
4. 对于离线唤醒场景，链路还会引入短信唤醒、重新登录、补发等流程，使链路分叉和合并关系更加复杂。
5. 传统依赖日志时间窗、人工比对业务字段的方法，准确率低、实时性差，不适合线上远控故障定位。

### 5.3 STSP 现网场景的具体挑战

在 STSP 远控场景中，同时存在两类链路结构：

1. 新能源车链路：`app-vehicle -> remote-service -> Kafka -> evgb-gateway -> Netty -> TBox`
2. 燃油车链路：`app-vehicle/fv-remote -> Kafka/EMQX -> fvgb-down-gateway -> MQTT -> TBox`

尽管车型架构不同，但二者都存在共同问题：

1. TBox 内部执行过程不可观测。
2. 下发链路与结果链路天然分段。
3. 无法统一进行端到端耗时分析。
4. 现有 MongoDB 主要承担业务管理职责，不适合直接承担高频、短时效的链路缝合关联存储。

因此，需要一种无需改造 TBox、又能适配多车型链路结构、并可在现有系统中低侵入落地的链路缝合方案。

## 六、发明内容

### 6.1 发明目的

本发明旨在解决终端黑盒设备不具备标准链路追踪能力时，下发链路与结果上报链路断裂、无法统一展示、无法量化黑盒区间耗时的问题，提供一种基于业务关联标识的远控链路自动缝合方法、系统、设备及存储介质。

### 6.2 技术方案

为实现上述目的，本发明采用如下技术方案：

一种基于业务关联标识的远控链路自动缝合方法，包括以下步骤：

#### S1：在远控指令下发阶段捕获原始链路上下文

在远控服务向终端设备下发远控指令之前，获取当前请求所在链路的追踪上下文信息，所述追踪上下文信息至少包括：

1. 原始 `traceId`
2. 当前关键下发节点的 `spanId`
3. 业务关联标识 `sendId`
4. 车辆标识 `VIN`
5. 指令类型 `commandType`
6. 业务维度信息
   业务维度信息包括租户标识、业务系统标识、业务渠道标识中的至少一种。

#### S2：建立临时关联映射

将 `sendId` 与所述追踪上下文信息写入临时关联存储，形成以下映射关系：

`sendId -> {traceId, parentSpanId, vin, commandType, tenantId, bizSystem, bizChannel, dispatchTime}`

优选地，所述临时关联存储采用 Redis，并对所述映射关系设置 TTL。

#### S3：使业务关联标识跨越终端黑盒

在向终端设备下发的消息中携带所述 `sendId`，使终端设备在执行远控指令后上报结果时原样携带该 `sendId` 返回云端。

#### S4：在结果上报阶段恢复原始链路上下文

远控服务或结果消费服务在接收到终端设备返回的结果消息后，解析所述 `sendId`，并根据所述 `sendId` 从所述临时关联存储中查询对应的原始链路上下文信息。

#### S5：构建上报链路 Span 并执行链路缝合

根据查询得到的原始链路上下文信息构建结果上报链路 Span，并采用如下任一方式完成链路缝合：

1. 使结果上报链路复用原下发链路的 `traceId`
2. 通过 Span Link 将结果上报 Span 与原下发关键 Span 建立逻辑关联

同时记录黑盒区间耗时：

`blackbox_duration = resultReceiveTime - dispatchTime`

其中，`dispatchTime` 为指令下发时刻，`resultReceiveTime` 为云端接收结果时刻。

#### S6：继续传播缝合后的链路上下文

以上报链路 Span 为根节点，将恢复后的链路上下文继续向推送服务、通知服务和查询服务传播，使后续操作均纳入同一业务链路分析视图中。

#### S7：异常与降级处理

当出现以下任一情况时，系统执行降级处理：

1. 结果消息中未携带 `sendId`
2. `sendId` 对应的关联数据不存在
3. 关联数据已过期
4. 临时关联存储不可用

降级方式为：

1. 创建独立 Trace 记录当前结果链路
2. 输出告警或异常日志
3. 不影响原始远控业务逻辑继续执行

### 6.3 对应的系统方案

一种基于业务关联标识的远控链路自动缝合系统，包括：

1. 上下文捕获模块，用于在指令下发前获取原始追踪上下文。
2. 关联存储模块，用于建立 `sendId` 与追踪上下文之间的映射关系。
3. 指令下发模块，用于向终端设备下发携带 `sendId` 的远控指令。
4. 结果解析模块，用于在结果消息中解析 `sendId`。
5. 上下文恢复模块，用于根据 `sendId` 恢复原始追踪上下文。
6. 链路缝合模块，用于将下发链路与上报链路恢复为完整业务链路。
7. 耗时计算模块，用于计算终端黑盒区间耗时和端到端耗时。
8. 降级处理模块，用于在关联失败时执行独立 Trace 记录和告警。

### 6.4 存储介质

一种计算机可读存储介质，其上存储有计算机程序，所述计算机程序被处理器执行时，实现如上所述的方法步骤。

### 6.5 有益效果

与现有技术相比，本发明至少具有以下有益效果：

1. 无需对 TBox 增加标准链路追踪能力，终端侧改造成本低。
2. 可将原本断裂的下发链路与上报链路恢复为完整业务链路。
3. 可利用 `sendId` 建立强关联，优于基于时间窗或日志模糊匹配的方式。
4. 可量化终端黑盒区间耗时，为性能分析与故障定位提供依据。
5. 可同时适配新能源车链路和燃油车链路，具有较强通用性。
6. 临时关联数据采用 Redis 存储并设置 TTL，兼顾性能、资源回收与实现复杂度。
7. 与 MongoDB 的业务管理逻辑解耦，减少对现有系统的侵入性改造。

## 八、具体实施方式

### 8.1 实施例一：新能源车在线场景

在新能源车在线远控场景中，App 发起远控请求后，经 `app-vehicle` 和 `remote-service` 处理后，指令通过 Kafka 分发至 `evgb-gateway`，再由 Netty 长连接下发至 TBox。

在该场景下，`remote-service` 在发送指令前执行以下动作：

1. 获取当前 Trace 的 `traceId` 和关键下发 Span 的 `spanId`
2. 读取本次远控请求对应的 `sendId`
3. 将 `sendId`、`traceId`、`spanId`、`VIN`、`commandType`、`dispatchTime` 等信息写入 Redis
4. 将 `sendId` 附带在下发给 TBox 的消息中

TBox 执行远控指令后返回结果，结果消息中携带原始 `sendId`。上游结果消费服务在消费到该结果后，根据 `sendId` 查询 Redis 中的映射关系，恢复原下发链路的上下文，并为结果处理流程创建上报 Span。随后将该上报 Span 与下发链路关键 Span 建立父子关系或 Span Link 关系，从而在观测平台中得到一条逻辑完整的远控链路。

### 8.2 实施例二：燃油车在线场景

在燃油车在线远控场景中，远控请求经 `fv-remote`、`fvgb-down-gateway`、EMQX 等节点下发到 TBox。由于 TBox 同样不具备 TraceContext 透传能力，因此在 `fv-remote` 下发前执行与实施例一类似的动作：

1. 获取当前链路的原始 Trace 信息
2. 将 `sendId` 与原始 Trace 信息写入 Redis
3. 指令消息携带 `sendId`
4. TBox 结果上报后，消费端根据 `sendId` 恢复上下文并缝合链路

该实施例表明，本发明不依赖特定下发协议，既适用于 Netty 长连接架构，也适用于 MQTT/EMQX 架构。

### 8.3 实施例三：离线唤醒场景

在车辆离线场景中，系统除写入主关联映射外，还可写入待执行指令队列，如：

`rc:pending:{vin} -> sendId`

当短信唤醒链路将车辆唤醒并重新上线后，系统根据车辆标识读取待执行队列中的 `sendId`，触发指令补发。补发后的执行结果仍以相同 `sendId` 回传，最终在结果处理阶段通过 `sendId` 与原始下发主线完成合并。

该实施例表明，本发明不仅适用于简单在线链路，也适用于链路存在分支和补发的复杂远控场景。

### 8.4 实施例四：关联存储的数据结构

优选地，Redis 中的主关联 Key 如下：

```text
Key: rc:trace:{sendId}
Value:
{
  "traceId": "xxx",
  "parentSpanId": "xxx",
  "vin": "LSVAU2A37Nxxxxxxx",
  "commandType": "DOOR_UNLOCK",
  "tenantId": "tenantA",
  "bizSystem": "stsp",
  "bizChannel": "chery-app",
  "dispatchTime": 1713930000000
}
TTL: 24h
```

离线待执行队列优选为：

```text
Key: rc:pending:{vin}
Value: {sendId}
TTL: 24h
```

### 8.5 实施例五：链路查询与展示

管理平台可基于 `sendId` 执行链路检索：

1. 根据 `sendId` 查询 Redis 获取 `traceId`
2. 根据 `traceId` 查询观测后端数据存储
3. 展示下发链路、上报链路及其缝合关系
4. 输出端到端耗时、黑盒耗时、唤醒耗时和补发耗时等指标

### 8.6 实施例六：异常降级策略

若结果消息缺失 `sendId`，或 Redis 中未查询到对应映射，则结果链路仍可作为独立 Trace 被正常记录。系统同时输出告警日志，用于提醒链路缝合失败，但不阻断业务结果上报及推送流程。

## 十、摘要

本发明公开了一种基于业务关联标识的远控链路自动缝合方法、系统、设备及存储介质。该方法在远控指令下发阶段获取原始链路追踪上下文，并以 `sendId` 为键建立临时关联映射；终端设备在执行远控指令后回传携带所述 `sendId` 的结果消息；云端在结果上报阶段根据 `sendId` 恢复原始链路上下文，并将结果上报链路与原下发链路进行缝合，从而形成完整业务链路。该方案无需终端设备具备标准链路追踪能力，可适配多车型、多协议远控架构，并可量化终端黑盒区间耗时，适用于车联网远控可观测性建设。

## 十一、附注

### 11.1 与现有技术的关键区别

本发明的关键区别在于：

1. 不要求终端设备部署链路追踪 SDK。
2. 不依赖消息中间件原生透传完整 TraceContext。
3. 不使用时间窗和日志模糊匹配实现离线拼接。
4. 利用业务唯一标识实现跨终端边界的强关联恢复。
5. 通过临时关联存储实现“下发预存、上报恢复、实时缝合”的闭环。

### 11.2 建议重点强调的创新表达

建议在专利代理撰写时强化以下表述：

1. 终端黑盒不可观测条件下的链路恢复。
2. 业务唯一标识驱动的跨边界上下文恢复。
3. 下发阶段预存映射、上报阶段恢复映射。
4. 多车型、多协议链路结构下的统一缝合方法。
5. 黑盒执行耗时的量化能力。
