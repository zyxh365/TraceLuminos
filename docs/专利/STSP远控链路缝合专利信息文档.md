# STSP远控链路缝合专利信息文档

## 1. 文档目的

本文档基于《[STSP远控链路缝合改造方案](/e:/projects/分布式链路追踪/workspaces/TraceLuminos/docs/STSP远控链路缝合改造方案.md)》整理形成，面向专利交底、法务评审及专利代理撰写使用，提炼其中可申请专利的技术问题、技术方案、创新点、实施方式及有益效果。

## 2. 拟定专利名称

**一种基于业务关联标识的远控链路自动缝合方法、系统、设备及存储介质**

可选名称：

1. 一种跨非可观测终端边界的分布式链路缝合方法及系统
2. 一种面向车联网远程控制场景的链路追踪关联方法及装置
3. 一种基于 `sendId` 的远控指令下发与结果上报链路缝合方法

## 3. 技术领域

本发明涉及分布式系统可观测性、车联网远程控制、消息链路追踪与云边端协同技术领域，尤其涉及一种在终端设备不具备链路追踪能力的条件下，对远控指令下发链路与结果上报链路进行自动关联和缝合的方法、系统、装置及存储介质。

## 4. 背景技术

在车联网远控场景中，一条完整链路通常包括：

`App -> TSP网关 -> 远控服务 -> 网关/消息中间件 -> TBox -> 网关/消息中间件 -> 远控服务 -> 推送服务 -> App`

该链路横跨 HTTP、Kafka、MQTT、Netty 长连接、短信唤醒、消息推送等多种协议与组件。

现有分布式追踪方案通常依赖标准 `TraceContext` 在各服务节点透传，但 TBox 属于终端黑盒设备，通常存在以下问题：

1. TBox 不具备 OpenTelemetry 等链路埋点能力，无法透传标准 Trace 上下文。
2. 指令从云端下发到 TBox 后，链路在设备边界处中断。
3. TBox 返回执行结果时，云端只能新建一条独立 Trace，无法与原下发链路自动合并。
4. 离线唤醒场景还会引入短信、登录、补发等额外分支，链路更长、更复杂。
5. 现有基于日志、时间窗口、人工检索的关联方式准确率低，难以支持实时问题定位和端到端耗时分析。

因此，亟需一种无需改造 TBox、又能将“下发链路”与“上报链路”在观测平台中恢复为完整业务链路的技术方案。

## 5. 要解决的技术问题

本方案重点解决以下技术问题：

1. 终端黑盒设备无法传递标准链路追踪上下文，导致链路在设备边界断裂。
2. 下发链路与结果上报链路分裂为两条 Trace，无法统一展示。
3. 无法准确量化 TBox 黑盒区间的处理耗时。
4. 新能源车与燃油车存在不同的远控链路结构，需要形成统一可复用的缝合机制。
5. 需在不改动现有业务管理库 MongoDB 主逻辑的前提下完成关联能力建设。

## 6. 核心技术方案

### 6.1 总体思路

本方案以业务侧天然存在的唯一关联标识 `sendId` 作为桥梁，在远控指令下发时保存 `sendId -> traceId / spanId / 业务维度` 的临时映射，在结果上报时根据 `sendId` 恢复原始关联信息，并通过 Span 关联机制将两段链路进行缝合。

### 6.2 关键步骤

#### 步骤一：下发阶段捕获原始链路上下文

在远控服务向 TBox 下发指令前，获取当前 Trace 的上下文信息，包括：

1. 原始 `traceId`
2. 当前关键下发节点的 `spanId`
3. 车辆 `VIN`
4. 指令类型 `commandType`
5. 租户、业务系统、业务渠道等业务维度
6. 下发时间 `dispatchTime`

#### 步骤二：建立 `sendId` 关联映射

将上述信息以 `sendId` 为主键写入 Redis，形成临时关联记录，例如：

`rc:trace:{sendId} -> {traceId, parentSpanId, vin, commandType, tenantId, bizSystem, bizChannel, dispatchTime}`

并设置 TTL，使映射自动过期，避免长期占用存储资源。

#### 步骤三：指令携带 `sendId` 穿越终端黑盒

在向 TBox 下发的消息中保留或附带 `sendId`。TBox 虽不支持 TraceContext 透传，但可以在执行结果上报时原样回传 `sendId`。

#### 步骤四：结果上报阶段恢复关联上下文

远控服务或结果消费服务收到 TBox 上报结果后，解析其中的 `sendId`，并从 Redis 查询对应的原始 Trace 信息，恢复下发侧的链路上下文与业务维度。

#### 步骤五：创建上报 Span 并完成链路缝合

基于查询得到的原始信息创建结果上报链路 Span，并通过以下方式实现缝合：

1. 让上报链路复用下发链路的 `traceId`，或
2. 通过 Span Link 将上报 Span 与下发关键 Span 建立关联

同时记录黑盒区间耗时：

`tbox_execute_duration = resultReceiveTime - dispatchTime`

从而在观测平台中形成一条可检索、可展示、可分析的完整远控业务链路。

#### 步骤六：异常与降级处理

当 `sendId` 缺失、Redis 未命中、数据过期或异常时，系统自动降级为记录独立 Trace，并保留告警与日志，不影响原有远控业务执行。

## 7. 方案关键创新点

### 7.1 基于业务唯一标识而非标准 TraceContext 进行跨终端关联

本方案不依赖终端设备支持标准链路追踪协议，而是利用业务链路天然存在的 `sendId` 实现跨设备边界的上下文恢复。

### 7.2 通过临时关联存储实现“断链重连”

在下发阶段提前落库映射关系，在上报阶段按 `sendId` 反查并恢复上下文，构建出适用于终端黑盒场景的链路缝合机制。

### 7.3 支持黑盒区间耗时量化

通过保存下发时间、在结果返回时计算间隔，可量化 TBox 执行耗时与链路黑盒区间耗时，弥补传统链路追踪无法覆盖设备内部执行过程的问题。

### 7.4 适配多车型多协议差异化架构

本方案同时适用于：

1. 新能源车链路：`remote-service -> Kafka -> evgb-gateway -> Netty -> TBox`
2. 燃油车链路：`fv-remote -> Kafka/EMQX -> fvgb-down-gateway -> MQTT -> TBox`

虽下发通道不同，但均复用统一的 `sendId + 临时映射 + 上报恢复 + 链路缝合` 方法。

### 7.5 与现有业务数据管理解耦

MongoDB 继续承担业务管理职责，Redis 专门承担链路缝合关联职责，避免侵入现有业务数据模型和业务读写逻辑。

## 8. 推荐保护点

### 8.1 方法类独立权利要求方向

可围绕以下步骤组织独立权利要求：

1. 获取远控指令下发时的原始链路上下文。
2. 提取并绑定业务关联标识 `sendId`。
3. 将 `sendId` 与原始 Trace 信息写入临时关联存储。
4. 将 `sendId` 随指令传递至终端设备。
5. 在接收终端返回结果时解析 `sendId`。
6. 根据 `sendId` 查询原始链路上下文。
7. 基于所查询的上下文构建上报链路 Span，并与下发链路建立关联。
8. 输出完整业务链路及黑盒区间耗时。

### 8.2 系统类权利要求方向

系统可包括：

1. 上下文捕获模块
2. 业务标识提取模块
3. 关联存储模块
4. 指令下发模块
5. 结果解析模块
6. 上下文恢复模块
7. 链路缝合模块
8. 耗时计算模块
9. 异常降级模块

### 8.3 从属权利要求可补充的限定点

1. 临时关联存储采用 Redis，并设置 TTL 自动过期。
2. 存储内容包含 `traceId`、`parentSpanId`、`dispatchTime`、`vin`、`commandType`、`tenantId`。
3. 缝合方式采用父子关系重建或 Span Link 关联。
4. 支持离线唤醒、在线直发、补发重试等多种远控场景。
5. 支持按 `sendId` 查询完整链路以及链路断裂点。
6. 支持黑盒耗时、唤醒耗时、补发耗时等指标计算。

## 9. 结合本项目的具体实施方式

### 9.1 新能源车实施方式

在新能源车链路中，远控服务在通过 Kafka 将指令下发到 `evgb-gateway` 前，记录 `sendId` 关联关系；TBox 通过 Netty 通道返回结果后，由结果消费端读取 Redis 中的关联信息，完成上报链路与原下发链路缝合。

### 9.2 燃油车实施方式

在燃油车链路中，`fv-remote` 在指令进入 `fvgb-down-gateway` / EMQX 下发前，先写入 `sendId` 关联关系；TBox 结果回传后，消费端按 `sendId` 恢复原始 Trace 信息并构建缝合后的上报链路。

### 9.3 离线唤醒场景

对于离线车辆，可在 Redis 中追加待执行队列键，例如：

`rc:pending:{vin} -> sendId`

待车辆被短信唤醒并重新上线后，再通过该映射补发指令并延续同一关联主线，从而实现离线唤醒场景下的链路贯通。

## 10. 有益效果

与现有技术相比，本方案至少具有以下有益效果：

1. 无需改造 TBox，不要求终端具备链路追踪能力。
2. 可将原本断裂的下发链路与上报链路恢复为完整业务链路。
3. 可精准定位链路断点与黑盒区间耗时。
4. 支持多车型、多协议、多链路结构的统一观测方案。
5. 通过 Redis TTL 自动回收，兼顾性能、时效性与实现成本。
6. 与现有 MongoDB 业务管理逻辑解耦，落地风险较低。
7. 支持管理平台按 `sendId` 反查完整链路，提升定位效率。

## 11. 与现有方案相比的区别点

相较于传统日志拼接、时间窗口匹配或要求终端埋点的方案，本方案的主要区别在于：

1. 不在终端设备内部植入追踪 SDK。
2. 不依赖消息中间件原生透传完整 TraceContext。
3. 不通过模糊时间窗口做离线拼接。
4. 采用业务唯一标识建立强关联。
5. 采用临时映射与链路恢复机制进行实时缝合。
6. 可显式计算终端黑盒区间耗时。
